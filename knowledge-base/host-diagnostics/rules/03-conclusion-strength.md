# 结论强度纪律

> 诊断工具最容易犯的错误不是漏检，而是**把观察说成了结论**。本文件规定结论的分级与表述纪律。
>
> 本文件的规范级别定义见领域 `README.md`。

## 1. 三档结论强度

每条结论**必须**标注强度，三档取一：

| 强度 | 含义 | 何时可用 |
|---|---|---|
| **已确认** | 证据直接且充分，无需进一步验证 | 客观事实且语义明确（注册表键存在、模块已加载、hosts 含某条目） |
| **推测** | 证据支持但不充分，需进一步验证 | 存在性成立但因果未验证；或依赖多个假设 |
| **超出覆盖** | 现有判据无法回答 | 见 § 3 |

**禁止**混用或省略强度标注。**禁止**用「可能」「疑似」「建议检查」这类措辞代替明确的强度分级——它们语义模糊，读者无法判断该采取什么行动。

**理由**：诊断结论会直接影响用户的处置决策（卸载软件、修改配置、联系支持）。不标强度，用户无法区分「确定是这个」与「也许有关」，从而做出代价不相称的处置。

### 各篇的强度基线

| 判据来源 | 典型强度 | 原因 |
|---|---|---|
| `reference/system-environment-hijack.md` | 多数「已确认」 | 注册表键存在与否是客观事实且语义明确 |
| `reference/module-injection.md` | 多数「推测」 | 存在可疑模块 ≠ 它导致了现象 |
| `reference/network-layered-probe.md` | 分层定位「已确认」，因果「推测」 | 能确定故障在哪一层，不能确定该层异常是否为主因 |

## 2. 相关性不等于因果

**禁止**由「检测到 X 且现象为 Y」直接判定「X 导致 Y」。

以下推理形态均**不成立**：

| 不成立的推理 | 为什么 |
|---|---|
| 装了某安全软件 + 程序卡顿 → 该软件导致卡顿 | 大量机器装同款软件且不卡 |
| 存在无签名模块 + 白屏 → 该模块导致白屏 | 该模块可能与渲染无关 |
| CPU 占用高 + 程序无响应 → CPU 不足导致无响应 | 因果可能相反（程序死循环导致 CPU 高） |
| 检出多项异常 → 异常越多问题越严重 | 多数异常与当前现象无关 |

**升级为「已确认」的唯一途径**：移除或停用该因素后现象消失，且恢复后现象重现。

⚠️ 但该验证属系统修改，不在诊断阶段职责内——**应该**作为建议提供给用户，由用户决策执行。见 `rules/01-diagnostic-safety.md § 1`。

**理由**：故障机器上通常存在多项「异常」，其中绝大多数与当前现象无关。不加约束的因果推断会让用户卸载无辜软件，问题却依旧存在。

## 3. 超出覆盖必须显式声明

无判据支撑时**必须**输出「超出覆盖」，**禁止**强行给结论。

以下情形**必须**声明超出覆盖：

- 现象不在 `reference/symptom-routing.md` 的路由表中
- 全部检测项通过但现象仍存在
- 采集因权限或环境限制未能完成（见 `rules/02-evidence-standards.md § 3`）
- 判定依赖本领域未覆盖的知识（服务端状态、业务逻辑、中间网络设备）

声明**应该**同时给出：已排除的项清单、建议的下一步方向。

**理由**：「未发现问题」与「无法判断」是两个完全不同的结论，混淆两者会让用户停止排查，或误认为问题不存在。

> 每篇 reference 的末节「本篇覆盖边界」即为此服务——它明确列出该篇判不了什么。

## 4. 风险计数不是故障计数

呈现结果时**应该**区分「发现异常项」与「确认致因」。

**不应**使用「共发现 N 项问题」这类表述——它隐含了「N 项都是问题」与「修完 N 项就好了」两个未经验证的判断。

推荐的呈现结构：

| 分组 | 含义 |
|---|---|
| **确认相关** | 已确认与当前现象有因果关系 |
| **需要关注** | 存在异常，与现象的关系待验证 |
| **仅供参考** | 与当前现象无关的环境信息 |

**理由**：外部工具采用「共发现 N 项风险信息」的计数模型，对用户友好但容易让人把「检出 47 个第三方模块」读成「有 47 个问题」。见 `reference/aha-doctor-teardown.md § 2.3`。

计数模型会驱动用户去「清零」——逐项处理与现象无关的检出项，付出代价却无收益。

> 这是 SHOULD：计数呈现在某些场景（如批量巡检）有其价值，但面向单次故障排查时应按相关性分组。
