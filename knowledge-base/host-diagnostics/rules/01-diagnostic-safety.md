# 诊断行为的安全约束

> 诊断工具会读取其他进程的内存布局、系统配置与网络状态，并可能执行系统修改。这些能力必须有硬性边界。
>
> 本文件的规范级别定义见领域 `README.md`。

## 1. 只读优先

诊断阶段**必须**只采集不修改。

**禁止**在诊断流程中执行任何系统写操作，包括但不限于：修改注册表、屏蔽或卸载模块、清除 DNS 缓存、重置网络配置、导入证书、终止进程。

修复动作**必须**与诊断分离：

- 诊断产出的是**证据与建议**，不是已执行的变更
- 每个修复动作**必须**由用户显式触发，不得作为诊断的自动后续
- 修复入口**应该**与诊断结果在界面上分离，避免误触

**理由**：诊断的前提是「现场未被改变」。一旦诊断过程本身修改了系统，后续排查失去基线，且无法区分现象变化是原故障还是诊断动作导致。

外部工具的实践印证了这一边界：其诊断模块除模块屏蔽外全部为只读采集，连服务控制都只使用查询 API。见 `reference/aha-doctor-teardown.md § 4.3`。

## 2. 写操作的确认与回滚

确需提供修复功能时，每个写操作**必须**满足三个条件：

| 条件 | 要求 |
|---|---|
| **明示影响** | 执行前告知用户将修改什么、可能的副作用、是否需要重启 |
| **可撤销** | 提供撤销入口；无法撤销的操作必须在执行前明确告知 |
| **记录原状态** | 修改前保存原值，供撤销与事后追溯 |

**不得**提供「一键修复全部」这类批量写操作而不逐项确认——批量操作使用户无法判断每项变更的必要性，且失败时难以定位。

**理由**：诊断工具的用户通常正处于故障状态，判断力受挫且倾向于接受任何建议。批量不可逆操作在此情境下风险最高。

⚠️ 模块屏蔽尤其危险：屏蔽错误的模块可能导致目标程序或其他程序无法启动。见 `reference/module-injection.md § 5.1`。

## 3. 提权最小化

主进程**不应**以管理员权限常驻。

需要提权的操作**应该**外包给独立的辅助进程，用完即退，主进程保持普通权限运行界面。

**理由**：

- 提权进程的界面暴露面更大（拖放、剪贴板等受 UIPI 限制，反而影响体验）
- 长期提权驻留扩大了漏洞被利用时的影响范围
- 诊断的大部分采集动作并不需要管理员权限

外部工具采用了这一结构：主程序与辅助进程清单均为 `asInvoker`，提权按需在运行时发起。见 `reference/aha-doctor-teardown.md § 3.4`。

⚠️ **但须权衡**：部分采集项（枚举其他用户的进程模块、读取受保护注册表项、抓取内核转储）确实需要提权。工具**必须**明确告知哪些检测项因权限不足而被跳过，**不得**在权限不足时静默返回不完整结果——那会导致「检测通过」的错误结论。

## 4. 采集数据的密级

诊断采集的数据**必须**视为含环境指纹的敏感信息。

以下采集项均含可识别信息：

| 采集项 | 含有 |
|---|---|
| 进程模块列表 | 机器上安装的软件构成 |
| 网络配置 | 内网结构、IP、DNS、代理地址 |
| 域名探测结果 | 用户所属地域、网络归属 |
| 硬件信息 | 设备型号、序列号类信息 |
| 用户目录路径 | 用户名 |

因此：

- 诊断产物**禁止**未脱敏上报
- 诊断产物**禁止**提交进版本库；相关文件模式**必须**列入 `.gitignore`
- 上报前**必须**告知用户将上传什么，并取得同意
- 日志与报告中的用户名、路径**应该**脱敏

**理由**：诊断数据的敏感性容易被低估——它不含密码，但足以刻画一台机器与其使用者。

> 若诊断涉及内存转储，其密级更高（可能含明文凭证与全量 PII），适用 `knowledge-base/dotnet-debugging/rules/01-dump-handling.md` 的更严格约束。

## 5. 禁止进程内注入

**不应**使用 API Hook、DLL 注入等手段采集数据。

监控类需求**应该**优先使用系统提供的旁路机制：

| 需求 | 推荐机制 | 而非 |
|---|---|---|
| DNS 解析监控 | ETW（DNS 客户端 provider） | hook `dnsapi` |
| 剪贴板监控 | 剪贴板格式监听器 | hook 剪贴板 API |
| 键鼠监控 | 系统钩子 API（进程外） | 进程内 hook |
| 网络流量统计 | ETW | hook Winsock |

**理由**（三条，任一成立即足以否决）：

1. **托管环境做进程内 hook 不稳定**——GC 移动对象、JIT 重编译与 hook 的地址假设冲突
2. **杀软误报率高**——注入行为在特征上与恶意软件难以区分，诊断工具反而会被拦截
3. **与 § 1 只读优先冲突**——注入本身就是对目标进程的修改

外部工具确实具备该能力（PE 中存在 Detours 特征节），但本领域**明确不继承**。见 `reference/aha-doctor-teardown.md § 5.1`。

> 这是一条 SHOULD 而非 MUST：存在旁路机制无法覆盖的采集需求时，可在充分评估后使用，但须记录理由并评估上述三项风险。
