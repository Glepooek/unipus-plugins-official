# 宿主进程环境诊断知识库

> 版本：1.0.0

> 面向 **Windows 桌面应用宿主进程的外部故障诊断**。收录当宿主进程「跑不动」时，如何从**进程外部的系统环境**中取证并定位故障源：第三方模块注入、安全软件拦截、网络不通、硬件资源不足、系统环境劫持。

本领域负责「程序本身没问题，但环境让它跑不起来」这一类故障。与 `dotnet-debugging` 互补而不重叠——后者负责进程**内部**（托管堆、线程、锁）的取证，本领域负责进程**外部**。

## 文档目的

让诊断工具的实现者与使用者能按「现象 → 候选故障源 → 取证手段 → 判据 → 结论强度」这条链路定位问题，而不必依赖个人经验重新摸索。

目标读者读完 `reference/symptom-routing.md` 即可确定该查哪几项，再按对应 reference 读懂具体判据。

## 适用范围与读者

- **适用范围**：Windows 桌面应用出现启动失败、白屏、卡顿、卡死、崩溃、网络异常等现象，且怀疑故障源在进程外部时的排查取证
- **平台**：仅 Windows（全部内容为 Windows 专有机制）
- **实现目标框架**：.NET 8+，兼容 .NET Framework 4.6.2+
- **读者**：诊断工具的开发者，以及需要定位宿主进程环境问题的支持与运维人员

## 收录判据

**判据进知识库，编排进 skill。**

检验标准：这条内容能独立成为「查一下就照着用」的判据吗？能 → 本领域。它是否必须知道「上一步查了什么」才有意义？是 → 属 skill，不收。

据此：

- 「IFEO 的 Debugger 键存在即为劫持」**收录**——单条可判
- 「先查环境劫持 → 无果则查注入 → 再无果则查网络」这条**编排不收**——它属于排查流程，由 `reference/symptom-routing.md` 以反查表形式承载导航，不作为规范条款登记

## 核心设计约束：知识库给方法，不给名单

本领域**不内置任何具体产品黑名单**（哪些安全软件、哪些 DLL 会导致故障）。

原因：这类名单是海量线上故障回流沉淀的产物，无法凭静态分析或推测复制。硬编一份猜测的名单比没有更糟——它会给出错误的确定性。

因此本领域收录：

- **判断框架**——如何认定一个模块可疑（签名、路径、厂商、加载方式）
- **冲突形态**——按类别而非具体产品描述
- **名单外置方案**——由使用方按自己的故障回流逐步积累为可维护数据

## 与既有领域的边界

| 已有领域 | 它负责 | 本领域负责 | 切线 |
|---|---|---|---|
| `dotnet-debugging` | 进程内部：托管堆、线程、锁的取证 | 进程外部：注入、拦截、网络、硬件 | 内 vs 外 |
| `dotnet` | 目标框架能跑在哪 | 运行环境是否被干扰 | 能不能跑 vs 跑不跑得动 |
| `csharp` / `wpf` | 怎么写才不出问题 | 代码没问题但环境有问题 | 预防 vs 环境排查 |

引用单向：本领域正文可指向上述领域，被指向方不反向声明。

**跨领域交接点**：一旦确认故障源在进程内部（托管堆增长、Dispatcher 死锁等），本领域到此为止，转交 `dotnet-debugging`。交接判据见 `reference/symptom-routing.md`。

## 规范级别

沿用 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 语义，与 `knowledge-base/csharp/README.md` 同一套定义。

| 级别 | 措辞 | 含义 |
|---|---|---|
| **必须 MUST** | "必须"、"禁止" | 硬性要求，无正当理由不得违反 |
| **应该 SHOULD** | "应该"、"不应" | 强烈建议，偏离需说明理由 |
| **可以 MAY** | "可以"、"建议" | 可选做法，按场景取舍 |

## enforcement 取值说明

本领域条目**几乎全部为 `review`**。

按知识库 README 的操作性检验「工具判的是该小节的实质，还是只是它的外壳」——本领域三类规则（诊断安全、取证质量、结论强度）都需人工判断意图与内容，无法由静态分析无歧义判定。这是本领域的性质决定的，不是治理数据缺失。

## 每篇 reference 的固定收尾

每篇 reference 的最后一节统一为「本篇覆盖边界」，写明该篇判不了什么。没有这一节，消费者无从知道判据的尽头在哪。

## 配套 skill 评估（2026-09-06）

按 AGENTS.md「引导器 / 传感器」自检要求所做的评估。**结论：待诊断工具形态明确后再定，当前不开发。**

### 两半是否配齐

配齐了，但都在知识库内部：

| 半边 | 承载物 |
|---|---|
| **引导器** | `reference/symptom-routing.md`——现象进、查什么出，含顺序与跨领域交接 |
| **传感器** | `rules/` 三篇 + 其余 reference 的判据表 |

缺的不是这一对，而是**把两者串成可执行循环的编排层**——即 `dotnet-diagnose-triage` 对 `dotnet-debugging` 所做的事。

### 为什么现在不做

三条理由：

| 理由 | 说明 |
|---|---|
| **消费者尚不存在** | `dotnet-diagnose-triage` 解读的是用户已取得的 SOS 输出，格式稳定且外部既有。本领域的证据由**待开发的诊断工具**产出，输出格式未定——现在写 skill 等于对着不存在的输入格式编排 |
| **阈值全部待校准** | 全部硬件阈值状态为 `待实测校准`。编排层若固化未校准的阈值，会把「初值」变成事实上的硬判据，与 `hardware-thresholds.md § 1` 冲突 |
| **判据可直接检索** | 72 条已具备 `anchor` 与 `summary`，`symptom-routing.md` 本身就是可读的编排。在工具形态明确前，直接读知识库的成本低于维护一个会过时的 skill |

### 若要做，边界如何划

与 `dotnet-diagnose-triage` **按故障位置切分，不按技术栈切分**：

| | `dotnet-diagnose-triage` | 潜在的 host-diagnostics skill |
|---|---|---|
| 输入 | dump / SOS 输出 / trace | 诊断工具的采集结果（进程外环境证据） |
| 判据源 | `knowledge-base/dotnet-debugging/` | `knowledge-base/host-diagnostics/` |
| 结论形态 | 进程内根因（死锁、泄漏、饥饿） | 进程外故障源（注入、拦截、网络、资源） |

交接点已由 `symptom-routing.md § 6.1` 定义，两者互转而非重叠。归属插件应为 `optimus-devops-plugin`（与 `dotnet-diagnose-triage` 同插件，便于共享交接约定）。

**重估时机**：诊断工具的输出格式确定后，或阈值完成首轮实测校准后。
