# 硬件资源判据

> 硬件资源不足是「卡顿」类现象的常见成因，但也是**最容易误判的一类**——因为高资源占用往往是结果而非原因。

## 1. 阈值的性质：可调参数，不是硬判据

⚠️ **本篇给出的全部阈值均为初始建议值，须在目标环境实测校准。**

### 1.1 为什么阈值不能硬编为判据

三个原因：

| 原因 | 说明 |
|---|---|
| **依赖硬件配置** | 4 核机器的 60% CPU 与 32 核机器的 60% 含义完全不同 |
| **依赖业务形态** | 视频会议应用占用 60% CPU 属正常，文本编辑器占 60% 属异常 |
| **依赖用户预期** | 开发机常年高负载是常态，办公机则不是 |

因此本篇的阈值**必须**作为**可配置参数**实现，不得写死在代码或判据里。

### 1.2 每个阈值须记录的三项元数据

| 元数据 | 用途 |
|---|---|
| **定值依据** | 这个数是怎么来的（行业通用值 / 微软文档 / 实测基线 / 经验值） |
| **校准状态** | `待实测校准` / `已在 X 环境校准` |
| **适用条件** | 该值在什么硬件与业务形态下有效 |

**理由**：没有依据的阈值是魔数。半年后无人知道"85%"是实测出来的还是随手写的，也就无人敢改。

### 1.3 禁止伪精确

**禁止**给出无依据的精确数字。

| 不可接受 | 应为 |
|---|---|
| 「CPU > 87.3%」 | 「CPU > 85%（经验值，待校准）」 |
| 「内存低于 512.7 MB」 | 「可用内存低于 10%（行业通用值）」 |

伪精确会让读者误以为该数值经过精密测算，反而比粗略值更有害。

### 1.4 校准方法

见 § 7。**本篇全部阈值当前状态均为 `待实测校准`。**

## 2. CPU

### 2.1 判据必须是「使用率 + 持续时长」

单看使用率毫无意义——任何程序在启动、加载、GC 时都会短暂占满 CPU。

| 观察 | 判定 | 强度 |
|---|---|---|
| 瞬时高但很快回落 | 正常 | 已确认 |
| 持续高于阈值超过持续时长 | 存在 CPU 压力 | 已确认（测量事实） |
| 系统整体高 vs 单进程高 | 分流依据，见 § 2.3 | — |

**初始建议值**（依据：经验值；状态：待实测校准）：

| 参数 | 建议初值 |
|---|---|
| 系统整体 CPU 阈值 | 85% |
| 单进程 CPU 阈值 | 按核心数归一化后 25% |
| 持续时长 | 30 秒 |
| 采样间隔 | 1 秒 |

### 2.2 必须按核心数归一化

单进程 CPU 使用率在不同工具中语义不同：有的以「单核 100%」为满，有的以「全部核心 100%」为满。

**必须**明确采用哪种口径并归一化，否则 32 核机器上"占用 100%"可能只是一个核心跑满（3% 总量）。

### 2.3 因果方向的判断

⚠️ **CPU 高与程序无响应之间，因果可能是双向的。**

| 观察 | 更可能的因果 |
|---|---|
| 目标进程 CPU 单核跑满 + 无响应 | **进程内部**死循环 → 转 `dotnet-debugging` |
| 系统整体 CPU 高 + 目标进程占比低 | 外部进程抢占 → 本篇 |
| CPU 不高但无响应 | **不是 CPU 问题** → 转死锁或阻塞排查 |

这是 `symptom-routing.md § 4` 分流判据的细化。

## 3. 内存

### 3.1 三个不同的指标

**必须**区分，它们回答不同问题：

| 指标 | 含义 | 耗尽的后果 |
|---|---|---|
| **物理内存可用量** | 尚未被占用的 RAM | 开始换页，性能下降 |
| **提交量 / 提交限制** | 已承诺的虚拟内存总量 | **分配失败，程序崩溃** |
| **进程工作集** | 该进程当前占用的物理内存 | 单进程指标，不直接致系统问题 |

⚠️ **提交量耗尽比物理内存耗尽更严重**——前者导致分配失败（崩溃），后者只是变慢。诊断"内存不足导致崩溃"时应看提交量，不是可用物理内存。

**初始建议值**（依据：经验值；状态：待实测校准）：

| 参数 | 建议初值 |
|---|---|
| 可用物理内存告警 | 低于总量 10% 或 1 GB（取大者） |
| 提交量告警 | 高于提交限制 90% |

### 3.2 虚拟内存配置

分页文件被禁用或设置过小时，提交限制约等于物理内存，**大幅提高分配失败概率**。

| 观察 | 判定 | 强度 |
|---|---|---|
| 分页文件已禁用 | 提交限制受限于物理内存 | 已确认 |
| 分页文件固定且较小 | 提交限制无法动态扩展 | 已确认 |

### 3.3 与托管内存的边界

⚠️ 本篇只判**系统级**内存压力。若怀疑目标进程自身内存持续增长（托管泄漏），属进程内部问题——转 `dotnet-debugging`，见 `symptom-routing.md § 6.1`。

区分点：系统整体内存紧张（多进程共同导致）→ 本篇；单一进程内存单调增长 → 进程内部。

## 4. 磁盘

### 4.1 三类指标

| 指标 | 判什么 | 建议初值（待校准） |
|---|---|---|
| **剩余容量** | 空间是否耗尽 | 低于 10% 或 5 GB（取大者） |
| **使用率 / 活动时间** | 是否饱和 | 持续 > 90% 且 > 30 秒 |
| **队列长度** | 是否积压 | 持续 > 2×主轴数 |

### 4.2 系统盘剩余容量的特殊性

系统盘空间不足的影响**远超普通数据盘**：分页文件无法扩展、临时文件写入失败、系统更新失败、用户配置文件写入失败。

因此系统盘**应该**使用比数据盘更保守的阈值。

### 4.3 SSD / HDD 判定

同样的队列长度与响应时间，在 SSD 与 HDD 上的含义完全不同。

| 观察 | 影响判定 |
|---|---|
| 系统盘为 HDD | 启动慢、加载慢属预期，阈值应放宽 |
| 系统盘为 SSD 但响应时间高 | 异常信号，可能是驱动、固件或健康度问题 |

**判定阈值前必须先确定介质类型**，否则 HDD 机器会持续产生误报。

### 4.4 磁盘压力的因果方向

与 CPU 同理：磁盘饱和可能是**其他进程**导致的，目标进程只是受害者。判定时须看**是谁在读写**，不只看总体使用率。

## 5. GPU 与渲染

### 5.1 硬件加速状态

对 WPF 宿主，这是比 GPU 使用率更重要的指标。

| 观察 | 判定 | 强度 |
|---|---|---|
| 渲染层级为硬件加速 | 渲染路径正常 | 已确认 |
| 渲染层级回退到软件渲染 | **CPU 承担渲染，界面卡顿** | 已确认 |
| 硬件加速被策略/配置禁用 | 同上，且是可修复的配置问题 | 已确认 |

**软件渲染回退是 WPF 卡顿的高频成因**，且容易被误判为程序性能问题。

### 5.2 回退的常见原因

| 原因 | 判定方式 |
|---|---|
| 驱动过旧或不支持所需特性 | 查驱动版本与日期 |
| 远程桌面 / VDI 会话 | 检出会话类型（`cli-process-toolbox.md § 7.5`）；⚠️ **VDI 环境的判据本领域未覆盖**，见 `symptom-routing.md § 8` |
| 注册表或组策略禁用 | 见 `system-environment-hijack.md § 3`（`DISABLEDWM`） |
| 第三方软件干扰渲染链 | 见 `module-injection.md § 4.1` |
| 虚拟机无 GPU 直通 | 环境判定 |

### 5.3 GPU 使用率

**初始建议值**（依据：经验值；状态：待实测校准）：持续 > 90% 且 > 30 秒。

⚠️ GPU 使用率的采集在不同显卡与驱动上差异较大，且多适配器（集显+独显）环境下需明确采集哪一个。**可靠性低于 CPU/内存指标**，判定时权重应相应降低。

## 6. CPU 型号与指令集兼容性

### 6.1 判什么

现代运行时与部分库依赖特定 CPU 指令集。目标机器不支持时，表现为**启动即崩溃**或**特定功能失败**，且错误信息通常不指向真实原因。

| 观察 | 判定 | 强度 |
|---|---|---|
| CPU 不支持程序所需指令集 | **必然失败** | 已确认 |
| CPU 型号早于程序支持的最低要求 | 可能失败 | 推测 |

### 6.2 为什么值得单列

这类问题有三个特征使其难以排查：

1. **确定性失败**——同一台机器必然复现，容易被误判为程序 bug
2. **错误信息无关**——通常报为通用异常，不提示指令集问题
3. **换机器就好**——导致排查者以为是"环境问题"却找不到具体环境差异

老旧机器或虚拟机（可能屏蔽了部分指令集）上出现"这台机器就是打不开"时，**应该**检查本项。

## 7. 阈值校准方法

### 7.1 校准步骤

1. **采集正常基线**：在无故障的目标环境采集各指标的正常范围（见 `rules/02-evidence-standards.md § 5`）
2. **确定分布**：取正常状态下的典型值与峰值
3. **定阈值**：阈值应高于正常峰值，留出余量避免误报
4. **记录**：更新本篇对应参数的定值依据与校准状态
5. **复核**：硬件更换或业务形态变化后重新校准

### 7.2 校准的最小样本

单台机器的基线不足以定阈值——须覆盖目标用户群的典型配置。至少应包含：最低配置机型、主流配置机型、以及特殊环境（VDI、虚拟机）各一。

### 7.3 无法校准时

拿不到基线时，**应该**：

- 沿用本篇建议初值
- 在报告中标注"阈值未校准，结论仅供参考"
- 相应降低结论强度为「推测」

**不得**因为未校准就省略该项检测——粗略判据仍优于无判据。

## 8. 本篇覆盖边界

### 本篇能判的

| 能判 | 强度 |
|---|---|
| 各项资源的当前测量值 | 已确认 |
| 是否超过设定阈值 | 已确认（相对阈值） |
| 硬件加速是否生效、渲染层级 | 已确认 |
| 磁盘介质类型（SSD/HDD） | 已确认 |
| CPU 是否支持所需指令集 | 已确认 |
| 资源压力是否为现象主因 | **推测**——因果方向常相反 |

### 本篇不能判的

| 判不了 | 原因 |
|---|---|
| **阈值是否适合本环境** | 未校准前阈值只是建议值 |
| **谁导致了资源压力** | 需进程级归因，本篇只判系统级压力 |
| **因果方向** | CPU 高可能是结果而非原因，见 § 2.3 |
| **托管堆内部的内存问题** | 属进程内部，转 `dotnet-debugging` |
| **GPU 指标的跨设备可比性** | 采集实现差异大，可靠性低于 CPU/内存 |
| **间歇性资源峰值** | 单次采样窗口外的峰值不可见 |
