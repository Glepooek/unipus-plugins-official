# 第三方模块注入检测

> **本领域价值最高的一篇。** 第三方 DLL 被注入宿主进程是白屏、卡顿、崩溃三类现象的头号成因。
>
> **【官方】依据**：aha_doctor 官方文档明确「白屏/卡顿类现象**通常是第三方软件引起**」——这是厂商基于海量线上故障回流给出的判断。见 `aha-doctor-teardown.md § 2.1`。

## 本篇的核心约束：给判断维度，不给名单

⚠️ **本篇不列举任何具体产品名。**

这不是回避，是本领域的核心设计决策：

- 「哪些模块会导致故障」这类名单，是海量线上故障回流沉淀的产物
- 静态分析或推测无法复制它——aha_doctor 的对应规则包（`ModuleDetect.dat`）是加密的，内容完全未知
- **硬编一份猜测的名单比没有更糟**：它会给出错误的确定性，让排查者相信一个未经验证的判断

因此本篇提供：**判断维度**（§ 2）、**注入手法识别**（§ 3）、**按类别的冲突形态**（§ 4）、**排除法**（§ 6）、**名单外置方案**（§ 7）。

具体名单由使用方按自己的故障回流积累——见 § 7。

## 本篇的结论强度基线

⚠️ **本篇多数判据只能给「推测」，不能给「已确认」。**

原因：「进程里存在一个可疑模块」与「这个模块导致了当前现象」之间，隔着一道静态检查无法跨越的鸿沟。一台正常运行的机器上通常也有若干第三方模块。

能给「已确认」的只有**存在性判定**（这个模块确实被加载了、它确实无签名）；**因果判定**一律是「推测」，需经 § 6 的排除法验证。

这与 `system-environment-hijack.md` 形成对比——那一篇多数可给「已确认」，因为注册表键存在与否是客观事实且语义明确。

## 1. 检测框架

四步，顺序固定：

```
枚举 → 验签 → 分类 → 判定
```

| 步 | 做什么 | 产出 | 失败时 |
|---|---|---|---|
| **1 枚举** | 列出目标进程已加载的全部模块 | 模块路径 + 基址 + 大小 | 权限不足则无法枚举，见下 |
| **2 验签** | 对每个模块验证数字签名，取签名主体 | 签名状态 + 厂商名 | 验签失败不等于无签名，见 § 2.1 |
| **3 分类** | 按系统 / 自身 / 第三方三分 | 缩小到第三方子集 | — |
| **4 判定** | 对第三方子集按 § 2 维度评估 | 可疑度排序 | 不产生「有害」结论 |

### 关于枚举的两个前提

**权限**：枚举 64 位进程的模块需要同为 64 位的诊断进程。32 位进程枚举 64 位目标会失败或只得到部分结果——这是静默的错误来源，须显式检查。

**时机**：模块是动态加载的。启动瞬间枚举与运行一段时间后枚举，结果可能不同。**排查白屏/崩溃类现象时，应在现象复现后立即枚举**，否则可能漏掉关键模块。

### 为什么必须分类后再判定

不分类直接看「有多少个模块」毫无意义——一个正常的 WPF 进程通常加载 100+ 个模块，其中绝大多数是系统 DLL 与 .NET 运行时。

**判定只在第三方子集上进行**。这一步能把候选从上百个缩到个位数。

## 2. 可疑判定维度

五个维度，**没有任何单一维度可以独立定案**——必须组合评估。

| 维度 | 低可疑 | 高可疑 | 权重 |
|---|---|---|---|
| **签名状态** | 有效签名 | 无签名 / 签名无效 / 已过期 | 高 |
| **签名主体** | 微软、已知大厂、宿主自身 | 未知主体 / 与功能不符 | 中 |
| **文件路径** | System32、程序自身目录、Program Files | 临时目录、用户目录、路径含随机串 | 高 |
| **加载方式** | 静态导入（在 PE 导入表中） | 非导入却已加载 → 运行时注入 | **最高** |
| **模块功能与宿主的关系** | 明确的依赖关系 | 与宿主功能无关 | 中 |

### 2.1 签名状态的三个陷阱

**① 验签失败 ≠ 无签名。** 验签需要访问证书吊销列表（CRL/OCSP），**离线或网络受限时会失败**。诊断工具必须区分「确认无签名」与「无法验证」——把后者报成前者是常见误判。

**② 有效签名 ≠ 无害。** 签名只证明「这个文件确实来自签名者且未被篡改」，不证明它与宿主兼容。**大量兼容性问题恰恰来自签名有效的正规软件。**

**③ 过期签名 ≠ 失效。** 若签名时带了可信时间戳，证书过期后签名仍然有效。判定时须看时间戳，不能只看证书有效期。

### 2.2 加载方式为什么权重最高

一个模块出现在进程里，只有两种可能：

- **静态导入**——它在某个已加载模块的 PE 导入表中，是正常的依赖关系
- **运行时注入**——它不在任何导入链上，是被某种机制塞进来的

后者本身就是强信号。正常的第三方依赖会通过导入表进入；**绕开导入表进入的，必然使用了 § 3 的某种注入手法**。

> ⚠️ 例外：延迟加载（`LoadLibrary` 显式调用）也不走导入表，且是完全正常的做法（插件系统、COM 组件）。因此"非导入"是**需要解释的信号**，不是"有罪"的证据。

### 2.3 判据模板

```
现象/输入：目标进程模块列表 + 各模块签名与路径信息
判据：某模块同时满足「非导入加载」+「无有效签名」+「路径在用户目录」
结论：该模块经运行时注入进入进程，来源可疑
强度：已确认（注入事实与签名状态）｜ 推测（是否为现象主因）
下一步：按 § 3 识别注入手法；按 § 6 排除法验证因果
```

## 3. 注入手法识别

识别手法的价值：**它告诉你去哪里找源头**，以及这个注入是全局的还是针对性的。

| 手法 | 特征 | 取证位置 | 影响面 |
|---|---|---|---|
| **AppInit_DLLs** | 注册表配置，加载 user32 的进程全中 | 见 `system-environment-hijack.md § 5.1` | 全局 |
| **SetWindowsHookEx** | 全局钩子，DLL 被注入到所有 GUI 进程 | 无直接注册表项，需看模块特征 | 全局 |
| **CreateRemoteThread** | 主动向目标进程注入 | 无静态痕迹，只能从结果观察 | 针对性 |
| **IFEO Debugger** | 启动重定向，可在中转时注入 | 见 `system-environment-hijack.md § 1` | 针对性 |
| **DLL 劫持（搜索顺序）** | 同名 DLL 放在优先搜索路径 | 比对模块路径与预期路径 | 针对性 |
| **ShellExecute Hooks** | COM 对象加载进调用进程 | 见 `system-environment-hijack.md § 5.2` | 全局 |

### 3.1 与环境劫持篇的交叉验证

**三种手法在两篇都有证据**（AppInit_DLLs、IFEO、ShellExecute Hooks）——注册表侧能看到配置，模块列表侧能看到结果。

**两侧都命中 = 强证据链**：配置存在 + 对应 DLL 确实在进程里，这比任何单侧证据都可靠。

**只有一侧命中时**：

| 情形 | 判读 |
|---|---|
| 注册表有配置，模块列表无对应 DLL | 配置未生效（开关关闭、Secure Boot、加载失败） |
| 模块列表有可疑 DLL，注册表无配置 | 用了无静态痕迹的手法（`CreateRemoteThread`、`SetWindowsHookEx`） |

### 3.2 DLL 劫持的判定

比对**实际加载路径**与**预期路径**：

| 观察 | 判定 | 强度 |
|---|---|---|
| 系统 DLL 从非系统目录加载 | **搜索顺序劫持** | 已确认 |
| 同名 DLL 在程序目录且系统目录也有 | 需比对签名判断哪个是预期的 | 推测 |

这是少数能给「已确认」的注入判定——系统 DLL 的预期路径是确定的。

## 4. 常见冲突形态（按类别）

⚠️ **本节按软件类别描述，不点名具体产品**——见篇首约束。

这些类别的共同点：**它们的正常工作方式就是注入其他进程**。因此检出它们不代表它们有恶意，只代表存在冲突可能。

| 类别 | 为什么注入 | 典型冲突形态 |
|---|---|---|
| **安全软件（HIPS / 沙箱 / 防护）** | 需要在进程内监控行为 | 拦截 API 调用导致卡顿；沙箱隔离导致文件/网络访问失败；误判导致模块被强制卸载 |
| **输入法** | 需要在目标进程内渲染候选窗 | 与宿主输入处理冲突导致输入异常、界面卡顿 |
| **屏幕取词 / 翻译工具** | 需要 hook 文本绘制 API | 干扰 GDI/DirectWrite 调用，导致渲染异常或崩溃 |
| **录屏 / 直播 / 会议工具** | 需要捕获窗口画面 | hook D3D/DWM 呈现链，**白屏的常见来源** |
| **远程控制 / 远程协助** | 需要接管输入与画面 | 同上，且可能改变窗口消息流 |
| **UI 增强 / 皮肤 / 窗口管理外挂** | 需要改变窗口外观行为 | 直接干预窗口过程，导致布局错乱或无响应 |
| **性能监控 / 游戏叠加层** | 需要在画面上叠加信息 | hook 呈现链，与硬件加速冲突 |

### 4.1 对 WPF 宿主的特有影响

WPF 的渲染路径（Media Integration Layer → DirectX → DWM）比传统 GDI 应用更容易受注入干扰：

| 被干扰的环节 | 现象 |
|---|---|
| **D3D 设备创建 / 呈现链** | **白屏**、渲染停滞、花屏 |
| **DWM 合成** | 窗口不刷新、透明区域异常 |
| **窗口消息流** | 输入无响应、焦点异常 |
| **GDI / DirectWrite 文本绘制** | 文字缺失、乱码、字体异常 |

> **这解释了为什么白屏在本领域排第一**：WPF 的白屏往往不是代码问题，而是渲染链被第三方干预。见 `symptom-routing.md § 3`。

### 4.2 硬件加速的交叉判据

若怀疑注入干扰渲染，一个**低成本验证手段**：临时禁用硬件加速（强制软件渲染）。

- 禁用后白屏消失 → 强烈指向渲染链被干扰（注入或驱动）
- 禁用后仍白屏 → 排除渲染链，转查其他成因

这是本篇少数能提供**主动验证**而非被动观察的判据。

## 5. 排除法：确认某模块与现象无关

> **本节比"找出可疑模块"更重要。** 排查的实际瓶颈通常不是"找不到可疑项"，而是"可疑项太多，不知道哪个是真的"。

四种排除手段，按成本排序：

| 手段 | 做法 | 能得出的结论 | 成本 |
|---|---|---|---|
| **时间线比对** | 模块所属软件的安装时间 vs 现象出现时间 | 安装在现象之后 → **可排除** | 极低 |
| **对照机比对** | 正常机器上是否也有该模块 | 正常机器也有且无现象 → **可疑度大幅降低** | 低 |
| **净启动比对** | 在干净环境（安全模式 / 新用户配置）复现 | 干净环境无现象 → 确认是环境因素，但未定位到具体模块 | 中 |
| **逐项停用** | 停用/卸载可疑软件后复现 | 停用后现象消失 → **确认因果** | 高，且可能不可行 |

### 5.1 唯一能确认因果的方法

**只有「逐项停用后复现」能把结论从「推测」升级到「已确认」。**

其余三种手段都只能降低或提高可疑度，不能定案。这是本篇结论强度基线的直接后果。

⚠️ 但停用操作**属于系统修改**，不在诊断阶段的职责内——诊断工具应给出建议，由用户决策执行。见 `rules/01-diagnostic-safety.md § 1 只读优先`（待产出）。

### 5.2 排除的记录价值

排除结果应显式记录并随排查过程传递。理由：

- 避免重复排查同一项
- 跨领域交接时（转 `dotnet-debugging`）是关键输入
- 「五类外部源全部排除」本身就是一条结论，指向进程内部

见 `symptom-routing.md § 6.1`。

## 6. 冲突名单的外置与维护

### 6.1 为什么名单必须外置

名单是**会变的数据**，判据是**稳定的逻辑**。把名单硬编进知识库或二进制会导致：

- 每次新增一条已知冲突都要改代码/改文档并重新分发
- 名单无法按部署环境定制（企业 A 的标准装机软件在企业 B 不存在）
- 名单一旦过时无人察觉——没有反馈回路

aha_doctor 的做法印证了这一点：它把规则放在独立的加密数据文件里，与执行引擎分离。见 `aha-doctor-teardown.md § 3.1`。

### 6.2 建议的外置形态

一份**可编辑的数据文件**，与诊断工具分离，至少含：

| 字段 | 用途 |
|---|---|
| 模块名 / 文件名模式 | 匹配依据 |
| 签名主体 | 比模块名更稳定的匹配依据 |
| 已知冲突现象 | 命中后给用户的说明 |
| 建议处置 | 加白名单 / 停用 / 更新版本 |
| 证据来源 | 这条是怎么确认的（工单号、复现记录） |
| 录入日期 | 用于定期复核 |

**「证据来源」字段是关键**——没有它，名单会逐渐积累无人能验证的条目，最终变成不敢删也不敢信的负债。

### 6.3 名单的积累方式

从**实际故障回流**积累，不从推测积累：

1. 用户报障 → 按本篇 § 5 排除法定位到具体模块
2. **确认因果后**（停用复现验证通过）才录入
3. 记录证据来源与日期
4. 定期复核：软件版本更新后冲突可能已消失

⚠️ **不要从"这个软件看起来可疑"录入**。未经因果验证的条目会污染名单，让后续排查者产生错误的确定性——这正是本篇篇首约束要防的。

## 7. 本篇覆盖边界

### 本篇能判的

| 能判 | 强度 |
|---|---|
| 某模块是否被加载进目标进程 | 已确认 |
| 某模块的签名状态与签名主体 | 已确认（须区分"无签名"与"无法验证"） |
| 某模块是否经运行时注入进入（非导入） | 已确认 |
| 系统 DLL 是否从非预期路径加载 | 已确认 |
| 注入使用了哪种手法（部分手法） | 已确认（有注册表痕迹的）｜ 推测（无痕迹的） |
| 某模块是否为当前现象的主因 | **推测**——除非经 § 5.1 停用验证 |

### 本篇不能判的

| 判不了 | 原因 |
|---|---|
| **某个具体模块是否"有害"** | 本领域不内置产品名单，见篇首约束与 § 6 |
| **有效签名的模块是否兼容** | 签名只证明来源与完整性，不证明兼容性 |
| **`CreateRemoteThread` / `SetWindowsHookEx` 的注入源头** | 这两种手法无静态痕迹，只能观察结果，无法反推是谁注入的 |
| **模块之间的相互影响** | 多个注入模块可能相互冲突，静态检查无法建模 |
| **注入的意图** | 正常功能、兼容性适配、恶意行为在静态层面形态相同 |
| **枚举时机之外的模块** | 动态加载的模块可能在枚举后才进入 |

### 与其他篇的交接

| 情形 | 转向 |
|---|---|
| 需判断可疑模块是否属安全软件 | `security-software.md` |
| 注入手法有注册表痕迹，需交叉验证 | `system-environment-hijack.md § 1 / § 5.1 / § 5.2` |
| 模块全部排除但现象仍在 | `symptom-routing.md` 的下一优先级 |
| 确认故障在进程内部 | `symptom-routing.md § 6.1` → `dotnet-debugging` |
| 需要枚举与验签的具体实现 | `dotnet-probing-techniques.md` |
